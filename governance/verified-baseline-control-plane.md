# KEFAYAT Ω — VERIFIED BASELINE CONTROL PLANE
## Active authority overlay v1.0 — 2026-09-05

### Purpose
Make the Palestinian educational system resumable and verifiable independently of any single chat, model, Work session, or vendor runtime. Models and tools are replaceable execution engines; authority lives in persisted contracts, state, evidence, and tests.

### Authority order
For project execution, apply the strongest applicable source in this order:
1. the user's latest explicit lawful requirement;
2. this active control-plane overlay;
3. `state/verified-state.json` and protected golden contracts;
4. frozen MASTER Ω governance and verified source evidence;
5. domain sources with preserved provenance;
6. generated inference or implementation choice.

Historical documents remain evidence, not competing active authority. A stale statement cannot override a later protected invariant.

### Protected P0 math invariant
For semantic/student-eye `A + B = R`, the canonical direction-sensitive engine request is `R = B + A`.
Reference: student-eye `٤ + ٣ = □` ⇐ engine request `□ = ٣ + ٤`.
Operand identities and their bound visuals are immutable. Commutativity does not authorize swapping. RTL/BiDi is not the authority. The rendered artifact seen by the learner is the final oracle.

### Baseline states
- `EVIDENCE_ONLY`: source exists but has not passed applicable qualification.
- `CANDIDATE`: intended replacement under test; never silently supersedes a verified baseline.
- `VERIFIED_SOURCE`: source artifact passed its stated source-level QA scope.
- `VERIFIED_RUNTIME`: target runtime behavior has passed the canonical runtime fixture and applicable gates.
- `RELEASED`: verified artifact promoted under an explicit claim scope.
- `REJECTED`: failed a blocking gate; previous verified baseline remains active.

Promotion is monotonic only with evidence. Version numbers, generation success, or CI completion alone do not prove runtime or field readiness.

### Candidate promotion gate
A candidate may replace a verified baseline only when all applicable P0/P1 gates pass on the exact artifact to be delivered. At minimum:
`IDENTITY → SEMANTIC → ARABIC → MATH → RENDER → ALL-PAGES → USER-EYE → REGRESSION → DELIVERY`.
If a gate fails, repair the candidate and repeat affected + non-regression tests. Never weaken a passing protected gate to make a candidate pass.

### Artifact identity
For requested files, the requested extension and delivered extension must match. Intermediate HTML/Python/Markdown is not a terminal PDF delivery. When hashing is available, the tested artifact hash must equal the delivered artifact hash.

### Independence from Work/chat
No authoritative decision, baseline, protected rule, blocker, or successful repair may exist only inside a conversation or Work session. Persist it in the repository and, where appropriate, evidence storage. A new executor resumes from persisted state, revalidates it, then continues from the last verified baseline—not from the last conversational claim.

### Resume transaction
Every autonomous run performs:
`LOAD AUTHORITY → LOAD VERIFIED STATE → CHECK HASH/IDENTITY → CHECK OPEN BLOCKERS → VERIFY LAST BASELINE → CHOOSE HIGHEST-VALUE SAFE ACTION → EXECUTE → TEST → ATTACK → REPAIR → REGRESSION → RECORD EVIDENCE → PROMOTE OR RETAIN BASELINE`.

### Fail-closed claims
Use `NOT_PROVEN` when evidence is absent. Use `BLOCKED` only after safe available routes are exhausted or a genuinely non-delegable permission/evidence dependency remains. Do not ask the user to perform technical work the system can perform itself.

### Human authority boundary
Autonomous authority covers reversible technical execution, validation, repair, packaging, repository maintenance, evidence recording, regression, and candidate promotion when gates objectively pass. Escalate only for irreversible/high-impact external action, credential/authorization decisions, conflicting authoritative requirements, or facts that cannot be obtained without invention.

### Current release posture
The source-artifact Golden Render evidence is preserved as verified within its stated scope. Platform-specific Gemini Gem acceptance remains `NOT_PROVEN` until an actual Gem runtime run of the canonical PDF fixture is observed. This limitation must not be inflated into failure of the protected source rule, nor misreported as runtime verification.
